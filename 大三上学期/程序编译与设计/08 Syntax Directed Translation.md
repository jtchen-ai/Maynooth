# 08 Syntax Directed Translation

## 38 解析器与语法分析基础

### 基本概念

- **解析器、上下文无关文法、歧义性、自顶向下和自底向上解析**
- **语法的设计**：适用于自顶向下解析的语法通常比自底向上解析使用的语法更难设计。
- **递归下降分析器**
- **LL(1) 分析器**

### 移位规约分析 (Shift-Reduce Parsing)

- **有效前缀**：在移位规约分析中，栈的内容始终是一个有效前缀——也就是说，某个右句型的前缀，该前缀不会比该右句型处理部分的结束更右。处理部分是在该句型最右推导的最后一个步骤中引入的子串。
- **有效项**：项是一个在体中有点的产生式。如果该项的产生式用于生成处理程序，并且可接受前缀包括点左侧的所有符号但不包括点下方的符号，则该项对可接受前缀是有效的。

### LR 分析器

各种类型的 LR 分析器通过首先为所有可能的可行前缀构建有效项集（称为 LR 状态），并跟踪每个前缀在栈上的状态来工作。有效项集指导 shift-reduce 解析决策。

- 如果存在一个在体末尾有点的有效项，我们倾向于进行 **规约**。
- 如果某个符号在某有效项中立即位于点右侧，我们倾向于将该符号的 **look-ahead 符号压入栈中**。

#### 1. 简单 LR 分析器 (SLR)

- 在 SLR 分析器中，我们对具有右侧点的有效项执行归约，前提是前瞻符号可以在该产生式的头部在某些句法形式中跟随。
- 如果不存在解析动作冲突，即对于没有任何一组项目，也没有任何前瞻符号，存在两个可以归约的产生式，或者既可以选择归约也可以选择移动，那么该语法是 SLR，并且可以应用这种方法。

#### 2. 规范 LR 解析器 (Canonical LR)

- 这种更复杂的 LR 解析器使用由可跟在底层产生式使用之后的预期符号集增强的项目。
- 只有在存在一个有效项目且点位于右端，并且当前预期符号是该项目允许的预期符号之一时，才会选择规约。
- 规范 LR 解析器可以避免 SLR 解析器中存在的某些解析动作冲突，但对于相同的语法，通常比 SLR 解析器有更多的状态。

#### 3. 前瞻 LR 分析器 (LALR)

- LALR 分析器通过合并具有相同核（忽略相关前瞻集的项集）的状态，提供了 SLR 和规范 LR 分析器的许多优点。
- 因此，状态数量与 SLR 分析器相同，但 SLR 分析器中存在的一些解析动作冲突可能在 LALR 分析器中消失。
- 在实践中，LALR 分析器已成为首选方法。

### 自底向上解析歧义文法

- 在许多重要情况下，例如解析算术表达式，我们可以使用一个有歧义的文法，并利用诸如运算符优先级之类的附加信息来解决移进与规约之间的冲突，或由两个不同产生式引起的冲突。
- 因此，LR 解析技术可以扩展到许多有歧义的文法。

### Yacc

- 解析器生成器 Yacc 接收一个（可能）有歧义的文法和冲突解决信息，并构建 LALR 状态。
- 然后它生成一个函数，该函数使用这些状态执行自底向上的解析，并在每次进行规约时调用相关的函数。

## 39 语法导向定义 Syntax-Directed Definitions (SDDs)

通过在文法规则的产生式中附加 **属性（attributes）** 来关联语言结构的信息。每个语法符号（非终结符或终结符）可以有多个属性，用于表示语义信息（如类型、值、代码等）。用 **语义规则（semantic rules）** 定义这些属性的计算方式。

| **产生式**            | **语义规则**      |
| --------------------- | ----------------- |
| `E → E1 + T` （中序） | `E.code = E1.code |

### 属性类型

#### 继承属性（Inherited Attribute）

- 一个非终结符 B 在语法树节点 N 上的继承属性，由其父节点（即产生式中 B 的父）的语义规则定义。
- 从 **父节点** 向 **子节点** 传递上下文信息（如变量类型、作用域等）。

#### 综合属性（Synthesized Attribute）

- 一个非终结符 A 在节点 N 上的综合属性，由其自身的产生式规则定义，仅依赖于子节点和自身的信息。
- 从 **子节点** 向 **父节点** 传递结果（如表达式的值、类型、代码等）。

### 注意！终结符：

- 可以有 **综合属性**（如词法分析器提供的值）。
- **不能有继承属性**（因为没有语义规则来定义它们）。

**例子：A → B C**

- **继承属性**：A 把某些信息传给 B 和 C（如类型、作用域）。
- **综合属性**：B 和 C 的值被用来计算 A 的值。

## 40 注解语法树 (annotated parse tree)

在语法树的每个节点上标注其属性值（如 `.val`）的树称为 **注解语法树**，它展示了属性在语法结构上的传播与计算过程。

### 如何评估解析树节点上的属性？

- 必须先计算一个属性所依赖的所有其他属性。
- 如果所有属性都是 **综合属性**，则可以按 **后序遍历（postorder traversal）** 的顺序进行计算。即：先处理子节点，再处理父节点。
- 对于同时包含继承和综合属性的 SDD，可能会出现 **循环依赖**，导致无法确定求值顺序。

### 依赖关系 (Dependencies)

**注意！** 属性之间不是独立的，有些属性的值必须在其他属性被计算之后才能算。这称作依赖关系。

- 哪个属性依赖于哪个？
- 哪些顺序可以安全地计算属性？

我们使用以下两种工具来表示依赖关系：

1. **依赖图（Dependency Graphs）**
2. **拓扑排序（Topological Ordering）**

## 41 依赖图 (Dependency Graph)

一个依赖图是一个 **有向图**，用来决定在给定语法树中如何对属性实例进行求值。

- **节点**：代表某个属性实例（如 `E.val`、`T.type`）
- **边**：从 `X.a` 到 `Y.b` 表示 `Y.b` 的值依赖于 `X.a` 的值

例如：E.val = E₁.val + T.val

那么就有两条边：E₁.val → E.val、T.val → E.val

### 构造规则

基于以上构造，我们可以总结出依赖图的构造规则：

对于每个产生式中的语义规则，根据其定义方式创建边：

1. 如果某条规则定义了非终结符 A 的 **继承属性** `A.inh`，而它依赖于另一个符号 B 的属性 `B.attr`，那么：
   - 创建一条边：`B.attr → A.inh`
2. 如果某条规则定义了非终结符 A 的 **综合属性** `A.syn`，而它依赖于子节点 N 上的属性 `N.attr`，那么：
   - 创建一条边：`N.attr → A.syn`

### 拓扑排序 (topological sort)

- 找到一条从节点到节点的线性序列，使得所有依赖关系都被满足。
- 如果依赖图中有环则不存在拓扑排序 → 无法安全求值 → 属性不可计算。

**步骤：**

1. **构造依赖图**：根据语义规则画出所有依赖关系
2. **进行拓扑排序**：找出一个合法的线性顺序
3. **按排序顺序计算属性**

## 42 S-attributed SDD

如果 SDD 中所有属性都是综合属性，没有继承属性，则称为 **S-attributed SDD**。

- 所有属性都从子节点向上合成，没有从父节点传给子节点的信息。
- 求值顺序是 **自底向上（bottom-up）**，可以用 LR 分析器 或 后序遍历 高效实现。

------

## 43 L-Attributed SDD

在产生式体中，依赖关系只能从左到右，不能从右到左。

允许继承属性，但有约束：

Xᵢ 的继承属性可以依赖于：

1. 父节点的属性
2. 左边兄弟的属性
3. ❌ **不能依赖右边兄弟的属性**

- 无“右兄弟依赖” → 避免了循环风险
- 适合自顶向下分析器（因为从左到右扫描）

### 例子分析

任何包含以下规则的都不能被 L-Attributed：

- `A.s` 是综合属性（由子节点 B 提供）
- 第一条 ✅ 合法（子 → 父）
- 第二条 ❌ `B.i` 依赖于 右边兄弟 C 的属性（C.c）

## 44 可控副作用的语义规则

SDD 是介于 **属性文法（Attribute Grammar）** 和 **翻译方案（Translation Scheme）** 之间的折中方案。

- **属性文法**：无副作用，只计算属性值
- **翻译方案**：允许副作用（如插入符号表、生成代码）



### 允许偶然副作用（incidental side effects）

- 只要这些副作用不影响属性求值顺序即可，比如：在任意拓扑排序下都能产生“正确”的翻译结果。

  

  

  

  





### 限制可接受的求值顺序：

- 无论用哪种合法顺序求值，都必须生成相同的翻译结果。



### SDT 的三大典型应用：

1. 语法树构造（Syntax Tree Construction）
2. 类型检查和类型结构（Type Checking and Type Structures）
3. 中间代码生成（Intermediate Code Generation）

## 45 可控副作用的语义规则 (续/补充)

SDD 是介于 **属性文法（Attribute Grammar）** 和 **翻译方案（Translation Scheme）** 之间的折中方案。

- **属性文法**：无副作用，只计算属性值
- **翻译方案**：允许副作用（如插入符号表、生成代码）

### 允许偶然副作用（incidental side effects）

- 只要这些副作用不影响属性求值顺序即可，比如：在任意拓扑排序下都能产生“正确”的翻译结果。
- 限制可接受的求值顺序：无论用哪种合法顺序求值，都必须生成相同的翻译结果。

### SDT 的三大典型应用：

1. 语法树构造（Syntax Tree Construction）
2. 类型检查和类型结构（Type Checking and Type Structures）
3. 中间代码生成（Intermediate Code Generation）

### 属性信息编码

属性可以编码以下信息：

- 类型表达式（如 `int`, `array[10] of int`）
- 内存宽度（如 `int` 占 4 字节）
- 兼容性规则（如是否可赋值、函数参数匹配）

## 46 语法导向翻译 Syntax-Directed Translation Schemes (SDTs)

一个上下文无关文法，其中在产生式体中嵌入了程序片段称为 **语义动作（semantic actions）**，可以出现在产生式的任意位置。

### 语义动作 (semantic actions)

- 将程序片段嵌入到产生式体中，通常写在花括号 `{ }` 中，在该产生式被使用时执行。
- 可能包含：赋值变量、插入符号表（symbol table）、输出中间代码（emit code）。
- 例如：`E → E₁ + T { print '+' }`
- 解析过程中直接执行动作无需显式构建语法树，节省空间和时间，特别适合 LR 解析器。

### 后缀翻译方案 (Postfix SDT)

- 所有语义动作都放在产生式体的最右边，常见于 S-attributed SDD，因为可以自底向上求值。

### 解析器栈 (Parser Stack)

- 存储文法符号（终结符和非终结符）当符号被弹出栈时，执行其关联的语义动作。
- 适用于 LR 解析器、移进-归约（Shift-reduce）解析。

### 左递归导致的问题

- 无限递归（在自顶向下解析器中）
- 语义动作位置错误（因为动作在产生式末尾）

### 实时代码生成 (On-the-fly code generation)：

- 在解析过程中直接生成目标代码或中间代码
- 不需要显式构造中间表示（如语法树）
- 更高效，节省内存
