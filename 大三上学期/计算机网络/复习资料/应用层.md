# 应用层

## TCP / IP Transmission Control Protocol/Internet Protocol.

### 计算机系统在网络上通信时会使用一些层，对于 TCP / IP，主要有4层：

- 应用层 Application layer

- 传输层 Transport layer

- 网络层 Network layer

- 链路层 Link layer

- 物理层 Physical layer（有些书说是5层）

## 网络应用架构

### 客户端-服务器架构

- 服务器：

	- 有一个始终在线的主机称为服务器，有一个永久且固定的 IP 地址

- 客户端：

	- 请求服务器服务的主机称为客户端，可能有动态 IP，不能和其他客户端直接通信，而是通过IP地址通过服务器进行连接

### P2P 架构(协议：BitTorrent)

- peer-to-peer 

	- 让多台主机可以直接通信而不需要服务器的帮助

- 参与特定文件分发的对等节点称为种子。对等节点可以下载等大小的文件块

	- 文件块

		- 现实操作： 

			- 当由于文件太大（4GB），BT 协议不会把它当作一个整体来传输。

		- 切分：

			-  这个 4GB 的 ISO 文件在生成“种子文件（.torrent）”的那一刻，就被逻辑上切分成了无数个等大小的小方块。

		- 数据： 假设每个块的大小是 4MB。那么这 4GB 的文件就被切成了 1024 个块。

			- 块 #1：0MB - 4MB

			- 块 #2：4MB - 8MB

			- ..........

			- 块 #1024：... - 4096MB

		- 意义： 

			- 你的下载软件不是非要按顺序（1, 2, 3...）下载，它可以先下载“块 #500”，再下载“块 #10”。

	- 种子

		- 定义： 拥有100% 完整文件（所有 1024 个块都有）并且正在上传给别人的用户。

		- 真实角色：

			- 初始种子： 

				- Ubuntu 官方发布镜像时，他们的服务器就是第一个“种子”。它拥有完整文件，开始向外分发。

			- 普通用户种子： 

				- 假设隔壁老王也就是个普通用户，他昨天就已经下载完了这 4GB 的文件。但他没有关闭软件，而是让软件保持开启状态。此时，老王的电脑就变成了一个种子。

		- 你的行为： 

			- 你的下载软件连接上了老王的电脑，因为他有你需要的全部数据。

	- 对等节点 (Peer / Leech)

		- 定义： 参与下载，但还没有下载完 100% 文件的用户。他们既是下载者，也是上传者。

		- 真实角色：

			- 你（0%）： 你刚开始下载，你是 Peer。你需要从别人那里拿数据。

			- 巴西的小李（50%）： 此时网络里还有个巴西用户小李，他下载了一半（拥有 512 个块）。他也是 Peer。

	- 关键互动（互通有无）：

		- 你发现老王（种子）太忙了，网速慢。

		- 但是你发现**小李（Peer）**虽然没下载完，但他手里刚好有“块 #100”到“块 #200”。

		- 于是，你的软件从“未完成”的小李那里下载了“块 #100”。

		- 同时，你下载好了“块 #1”，发现小李刚好没有“块 #1”，你的软件会自动把“块 #1”上传给小李。

### 同一主机

- 两个进程通过进程间通信 interprocess comunication 相互通信

- 由操作系统定义

### 不同主机

- 套接字 Sockets:  

	- 进程通过称为套接字的软件接口向网络发送消息，并从网络接收消息。（可以想象是客户端/服务器 和 TCP 连接中间的门）

- 接收进程需要有地址，进程必须具有标识符，标识符包括与主机进程相关的 IP 地
址（128.119.245.12）和端口号

- 两个进程通过计算机网络交换信息相互通信,他们构成了进程对

	- （例如下载文件的客户端和上传文件的服务器通过P2P交换文件）

## **Web 和 HTTP**

http://www.someSchool.edu/someDepartment/p<br>
### 网络有三个组成部分：

- 统一资源定位器 Uniform Resource Locator（URL）：

	- 作为网络资源的系统。

- 超文本传输协议 Hyper Text Transfer Protocol（HTTP）：

	- 规范浏览器与服务器之间的通信。

- 超文本标记语言 Hyper Text Markup Language（HTML）：

	- 定义网页的结构、组织和内容。

### 当用户请求网页（例如点击超链接）时，

- 非持久 Non-persistent HTTP: 

	- 最多通过 TCP 连接发送一个对象

- 持久 HTTP：

	- 通过单一 TCP 连接发送多个对象

- 会发生

	- 浏览器会向服务器发送页面中对象的 HTTP请求消息。

	- 服务器接收这些请求，并以包含对象的 HTTP 响应消息进行响应。

### RTT(往返时间 round-trip time)

- 从客户端到服务器再返回的时间

- 非持久 HTTP 响应时间 = 2RTT+ 文件传输时间

### 例子

- **200 OK**

- **301 Moved Permanently 永久搬迁**

- **400 Bad Request   **糟糕的请求**

- **404 Not Found    未找到

- **505 HTTP Version Not Supported 版本不支持**

## DNS 域名系统（Domain name system）

主机通过IP 地址来标识：121.7.106.83，而人类用名字：maynoothuniversity.ie<br>DNS 是一种目录服务，提供网络中主机名称与其 IP 地址之间的映射<br>
### 1. 浏览器**提取主机名**

- 你的 Chrome 浏览器接收到你输入的完整长串 URL。为了知道要把请求发往何处，Chrome 的内部代码首先会解析这个字符串。它会忽略前面的协议部分（https://）和后面的路径部分（/video/BV...），精准地切割出服务器的主机名（域名）： www.bilibili.com

### 2. 主机名传递给客户端的 DNS 应用。

- 传递过程： 

	- Chrome 浏览器程序会发起一个系统调用（比如 Windows API 中的 getaddrinfo 函数），实际上就是对 Windows 系统说：“嘿，操作系统，我需要知道 www.bilibili.com 的 IP 地址，帮我查一下，我等你结果。

### 3. DNS 客户端向 DNS 服务器发送包含主机名的查询

- 谁是“DNS 服务器”？ 你的 Windows 电脑在连接家里 Wi-Fi 时，路由器通过 DHCP 协议自动告诉了电脑：“以后有 DNS 问题，就去问这两个 IP 地址（例如：114.114.114.114 或者你当地电信运营商提供的 DNS 服务器 IP）”。

- 发送过程： Windows 的 DNS Client 服务接收到 Chrome 的请求后，会构建一个真实的 DNS 查询数据包（UDP 协议，端口 53）。

- 数据包内容： 这个数据包里以二进制格式写着：“查询问题：A 记录，域名：www.bilibili.com”。

- 物理传输： 这个数据包从你的笔记本网卡发出 -> 通过 Wi-Fi 传给家里路由器 -> 路由器通过光猫经过运营商光纤网络 -> 最终抵达了运营商机房里的那台 DNS 服务器

### 4. DNS 客户端最终会收到包含主机名 IP 地址的回复

### 5. 一旦浏览器从 DNS 接收到 IP 地址，就可以发起与 HTTP 服务器的 TCP 连接

- 交还 IP： 

	- Windows 操作系统完成了之前的系统调用，把查询结果 119.29.29.29 交还给了等待中的 Chrome 浏览器。

- 发起连接： 

	- Chrome 终于拿到了它梦寐以求的目标 IP。现在，Chrome 的网络组件会向这个 IP 地址（119.29.29.29）的目标端口（HTTPS 默认为 443）发起一个标准的 TCP 三次握手（发送第一个 SYN 数据包）。

## CDN 内容分发网络(Content Distribution Network)

CDN 本质上是一组分布在全球各地的服务器，目的是加快网页内容的传输速度。<br><b>套接字编程</b><br>开发者必须决定是TCP还是UDP<br>
### TCP 是面向连接的 connection oriented，提供一个可靠的字节流通道，使数据在两个终端系统之间流动（3次握手）
### UDP 是无连接的，能够将独立的数据包从一端系统发送到另一端系统，且没有任何传输保证。
