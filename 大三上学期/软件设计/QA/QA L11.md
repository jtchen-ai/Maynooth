# QA L11 



## **1. 使用组合设计模式有哪些优势？**

- **在树状结构中，你可以统一对待组合对象（分支）和单个对象（叶节点）**。注意在这个例子中，我使用了两个通用方法：`printStructures()` 和 `getEmployeeCount()`，以便从组合对象结构（如校长或部门主管）和单个对象结构（即叶节点，如数学老师 1）中打印结构并获取员工数量。
- 使用这种设计模式来**实现“部分-整体”层次结构**是非常常见的。
- 你可以轻松地**向现有架构添加新组件**，或者从架构中删除现有组件。

**2. 使用组合设计模式相关的挑战有哪些？**

- 保持子节点的顺序较难
- 不能轻易删除不可变对象。
- 你可以轻松添加新组件，但这方面的支持可能会在未来**导致维护开销**。有时，你想处理一个具有特殊组件的组合对象。这种约束可能会导致额外的开发成本，因为你可能需要实现动态检查机制来支持这一概念。

**3. 在这个例子中，你使用了列表（List）数据结构。但我更喜欢使用其他数据结构。这样可以吗？**

当然可以。没有通用的规则。你可以自由使用你偏好的数据结构。GoF（设计模式四人帮）证实了**并非必须使用任何通用数据结构**。

## **4. 如何将迭代器设计模式与组合设计模式连接起来？**

再过一遍我们的例子。如果你想检查组合对象架构，你可能需要遍历这些对象。换句话说，如果你想**对分支进行特定活动**，你可能**需要遍历其叶节点和非叶节点**。迭代器模式通常与组合模式一起使用。

**5. 在你实现的接口中，你只定义了两个方法：`printStructures()` 和 `getEmployeeCount()`。但在组合类（`CompositeEmployee`）中，你使用了其他方法来添加和移除对象。为什么不把这些方法放在接口里？**

很好的观察。GoF 讨论过这一点。让我们看看如果你把 `addEmployee(...)` 和 `removeEmployee(...)` 方法放在接口里会发生什么。叶节点需要实现添加和移除操作。但在这种情况下这有意义吗？显而易见的答案是否定的。这看起来可能让你失去了透明度，但我认为你拥有了更高的安全性，因为我屏蔽了叶节点中无意义的操作。这就是为什么 GoF 提到这种决定涉及安全性与透明度之间的权衡。

**问题主旨** 为什么管理子节点的方法（如添加和删除）没有定义在统一的顶层接口中，而是只放在了具体的组合类里？



**回答主旨** 这是一个在**“安全性”**和**“透明性”**之间做出的权衡。 作者选择了**安全性**。如果把这些方法放在接口里，叶子节点（比如普通员工）就**必须被迫实现这些对它毫无意义的操作**，这容易出错。只在组合类里定义这些方法，虽然牺牲了让所有对象看起来完全一致的“透明性”，但能**防止在叶子节点上执行错误的操作**，从而更安全。





**6. 我想用抽象类代替接口。这允许吗？**

在大多数情况下，简单的回答是肯定的。但你需要理解抽象类和接口之间的区别。在典型场景中，你会发现其中一个比另一个更有用。因为我只展示简单易懂的例子，你可能看不出两者有太大区别。特别是在这个例子中，如果我使用抽象类而不是接口，我可能会在抽象类定义中放入 `getEmployeeCount()` 的默认实现。虽然你仍然可以争辩说，使用 Java 的 `default` 关键字，你也可以达到同样的效果，如下所示：

Java

```
interface IEmployee
{
    void printStructures();
    //int getEmployeeCount();
    default public int getEmployeeCount()
    {
        return 0;
    }
}
```
