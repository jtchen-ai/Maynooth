# 问答 书本

## **问题 1：使用外观模式的主要优势是什么？**

回答：

**应用场景：**如果一个系统包含很多子系统，管理所有这些子系统会变得非常棘手，客户端如果要单独和每个子系统进行交互，操作起来会很困难。在这种情况下，外观模式就非常有用。

- 它给客户端提供了一个简单的接口。简单来说，你不需要把复杂的子系统展示出来，只需要向客户端提供一个简化的接口。
- 这种做法还能把客户端和子系统分离开，从而降低它们之间的耦合度。此外，它还能减少客户端需要处理的对象数量。



## **问题 2：我看到外观类使用了组合的方式。这是故意的吗？**

回答：是的。通过这种方式，你可以很方便地访问每一个子系统里的方法。



**问题 3：看起来外观模式并不强制禁止我们直接连接子系统。这个理解对吗？**

回答：是的。外观模式并没有把子系统的类或接口**完全封装起来（没用到final）**。它只是提供了一个简单的接口或者说一层结构，让你操作更方便。你完全可以自由地暴露子系统的任何功能，

但在那种情况下，

- 你的代码可能会显得很乱，
- 同时你也失去了使用这个模式带来的所有好处。



## 问题 4：它和适配器设计模式有什么区别？

回答：

- 在适配器模式里，你是试图改变一个接口，让客户端感觉不到接口之间的差异

  (为了解决两个本来不兼容的接口无法一起工作的问题)。

- 而外观模式是简化接口。它给客户端展示的是一个简单的交互接口，而不是复杂的子系统。



## 问题 5：一个复杂的子系统应该只有一个外观类。这对吗？

回答：完全不对。你可以为一个特定的子系统创建任意数量的外观类。



## 问题 6：我可以在外观类里添加更多的东西或逻辑吗？

回答：是的，你可以。



## 问题 7：使用外观模式有什么挑战？

回答：子系统是和外观层连接在一起的。所以，

- 你需要维护额外的一层代码，也就是说你的代码库会变大。
- 当子系统的内部结构发生变化时，你也得在外观层里配合修改这些变化。
- 另外，开发人员需要学习这个新的层，尽管他们当中有些人可能已经知道如何高效地直接使用底层的子系统或 API 了。



## 问题 8：它和中介者设计模式有什么区别？

回答：

- 在中介者模式的实现里，子系统是知道中介者存在的。它们之间会互相交流,，中介者为了协调多个线程。

- 但是在外观模式里，子系统并不知道外观类的存在，而且通信是单向的，只能从外观类传到子系统。



## 问题 9：看起来要实现外观模式，我得写很多代码。这个理解对吗？

回答：并不一定。**外观模式的代码量由实际需求决定，并非固定需要编写大量代码**。比如在前面的实现例子里，如果你只考虑一种类型的机器人，比如只考虑 Milano 或者 Robonaut，并且如果你不想提供机器人的销毁机制，或者想忽略说明书，也就是例子里的两个静态方法，你的代码量会大大减少。我保留所有这些内容只是为了演示得更完整。



**按需暴露功能**：不需要把子系统的所有功能都封装进外观类，只需编写客户端真正需要调用的那部分功能接口。

**业务复杂度**：涉及的子系统数量越少，或者需要简化的逻辑越简单，外观类的代码量就越少。





# 问答环节

1. 使用外观模式的主要优势是什么？

结论：主要优势是简化了使用过程并降低了耦合度。

原因：外观模式通过提供一个统一的高层接口，把**底层子系统的复杂性隐藏了起来**，这样客户端就不需要了解子系统内部的类是如何交互的，代码也会变得更加清晰和易读 。





2. 我看到外观类使用了组合关系。这是故意的吗？

结论：是的，这是为了能调用子系统的功能。

原因：外观类（如 RobotFacade）内部**需要持有子系统对象**（如 RobotHands, RobotBody）的**引用**，这样当客户端调用外观类的方法时，外观类才能把**请求委托给这些具体的子系统对象去执行** 。





3. 在我看来，外观模式并不限制我们直接连接子系统。这种理解正确吗？

结论：这种理解是正确的。

原因：外观模式只是提供了一个更简单的入口来处理常见任务，它并没有强制禁止你绕过它（就是没有设计成private）。如果你需要用到子系统里某些高级或特殊的功能，你依然可以直接访问底层的子系统类。

public class Client {
    public static void main(String[] args) {
        
        // ==========================================
        // 场景 1：普通用户（使用外观模式）
        // ==========================================
        // 只需要造一个标准的机器人，不想关心具体细节。
        // 直接找 Facade，简单、省心。
        RobotFacade facade = new RobotFacade();
        facade.constructMilanoRobot();


        // ==========================================
        // 场景 2：高级用户（直接连接子系统）
        // ==========================================
        // 需求：我的机器人坏了，我只想要单独维修“手部”，不需要造个新机器人。
        // Facade 没有提供 "repairHand()" 方法，这时候我就必须绕过它。
        
        System.out.println("--- 高级用户：直接访问子系统 ---");
        
        // 1. 直接实例化子系统类
        RobotHands rawHands = new RobotHands();
        
        // 2. 调用外观类没有暴露的“高级功能”
        // 这种操作是允许的，外观模式并没有把子系统类设为 private
        rawHands.specialRepair(); 
    }
}





4. 它与适配器设计模式有什么不同？

结论：它们的目的完全不同。

原因：适配器模式通过转换接口，是为了解决两个本来不兼容的接口无法一起工作的问题；而外观模式则是为了给一组复杂的接口提供一个统一且简化的界面，让系统更容易被使用 。





5. 我可以在外观类中添加更多的东西或逻辑吗？

结论：可以，外观类通常包含协调逻辑。

原因：外观类不仅仅是简单的转发请求，它通常需要把各个子系统的方法按照正确的顺序组合起来（比如在示例中，构建机器人需要先创建身体，再创建手，最后上色），这就涉及到了业务逻辑的编排 。





6. 与外观模式相关的挑战是什么？

结论：外观类本身容易变得过于**庞大和复杂**。

原因：因为外观类集成了子系统的所有功能入口，随着子系统变得越来越复杂，外观类里的代码可能会急剧膨胀，变成一个难以维护的“上帝对象”。





7. 一个复杂的子系统应该只有一个外观类。这正确吗？

结论：通常是这样，但不是绝对的。

原因：一般情况下一个外观类就够用了，而且经常设计成单例模式。但如果子系统特别大，**为了避免外观类太大**，也可以把它拆分成几个外观类，或者分层级来使用。

### 

8. 与外观模式相关的挑战是什么？

结论：可能会隐藏子系统的重要功能或降低灵活性。

原因：虽然简化了接口，但如果是为了追求极致的简化，可能会让一些**需要精细控制的高级功能**无法通过外观类访问，导致高级用户觉得受限。





9. 它与中介者设计模式有什么不同？

结论：它们的通信方向和目的不同。

原因：外观模式是单向的，主要是为了给客户端提供方便，让客户端调用子系统；而中介者模式是多向的，它主要是为了协调**多个对象（同事类）之间**的**交互**，让它们互不干扰，逻辑在系统内部。







10. 在我看来，要实现外观模式，我必须写很多代码。这种理解正确吗？

结论：这是一种误解，实际上它能减少总的代码量。

原因：虽然你需要编写一个额外的外观类，但这只是把原本散落在客户端各处的复杂调用逻辑集中到了一个地方。对于客户端来说，原本需要写几十行代码来协调子系统，现在只需要调用外观类的一行方法，大大减少了重复代码 5。
